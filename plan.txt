BAILONGO — PLAN DE CONSTRUCCIÓN DE LA APP FINAL (FLUTTER)
================================================================================
Versión: 1.0
Base: BailonGO_TT1_DOCUMENTACIÓN.pdf (TT1) + prototipo Android/Kotlin existente
Objetivo: migrar/reconstruir el prototipo a la arquitectura final descrita en el
documento, multiplataforma (Android + iOS), offline-first, con backend Firebase.

--------------------------------------------------------------------------------
0. RESUMEN DE DECISIONES (tomadas del documento, cap. 6)
--------------------------------------------------------------------------------
- Framework móvil .......... Flutter (Dart)            [doc 6.5]
- Estimación de pose ....... MediaPipe BlazePose       [doc 6.1] (33 landmarks)
- Base de datos ............ Cloud Firestore (NoSQL documental) [doc 6.2]
- Autenticación ............ Firebase Authentication   [doc 6.2]
- Almacenamiento media ..... Cloud Storage for Firebase[doc 4.6.3.5]
- API Backend .............. Firebase Cloud Functions  [doc 6.4]
- Evaluación alineación .... Distancia euclidiana ponderada por fotograma [doc 6.3.1]
- Evaluación ritmo ......... DTW con banda Sakoe-Chiba  [doc 6.3.2]
- Precisión total .......... 0.6*alineación + 0.4*ritmo [doc RNF-06]
- Patrón offline-first ..... réplica local + sync bidireccional last-write-wins [doc 5.3.3]

Decisiones NO fijadas por el doc (elección recomendada para este plan):
- Gestión de estado ........ Riverpod (alternativa: Bloc)
- Estructura ............... Clean Architecture por capas (data/domain/presentation)
                             organizada por features.
- Persistencia local ....... Cache nativa de Firestore (offline) + Hive/Drift solo
                             para la cola de sync y datasets pesados de landmarks.
- Router ................... go_router (rutas declarativas, deep-link friendly).

2. MODELO DE DATOS (Firestore, doc 5.3.3 / Figura 7)
--------------------------------------------------------------------------------
USERS            { uid, nombre, email, fotoUrl, nivel, createdAt, settings }
CATALOG          { pasoId, nombre, descripcion, mediaUrl(video ideal),
                   duracionCicloSeg, orden }
REFERENCE_DATA   { pasoId -> ref a CATALOG, landmarks: [ {frame, vector15[] } ... ] }
HISTORY          { intentoId, uid, pasoId, scores:{ritmo, alineacion, total},
                   deviceInfo, timestamp, synced:bool }
GLOBAL_METRICS   { pasoId, promedios..., updatedAt }  (asíncrono, analítica)

Local (réplica/offline):
  - Cache Firestore (perfil activo, catálogo, mejor marca).
  - Cola de intentos pendientes (synced=false) -> Hive/Drift.
  - Cache parcial de REFERENCE_DATA del paso en curso.

    puntajes coincidan dentro de tolerancia (test de regresión del algoritmo).

6. FASES DE CONSTRUCCIÓN (orden recomendado)
--------------------------------------------------------------------------------
FASE 1 — Cimientos (PRIMERA PARTE, ver prompt aparte)
  - Proyecto Flutter + dependencias + tema Material 3 + go_router.
  - Integración Firebase (Auth, Firestore, Storage) con firebase_options.
  - Shell de navegación: Scaffold con Drawer (RF-01) y rutas placeholder
    (Perfil / Catálogo / Configuración).
  - Módulo Auth completo: login + registro (email/contraseña), guardas de ruta,
    persistencia de sesión, logout. (Google/Facebook se dejan para fase posterior.)
  - Entidad User + repos + providers (Riverpod).
  Entregable: app que arranca, registra/inicia sesión y navega entre secciones vacías.

FASE 2 — Catálogo + datos
  - Modelo de datos Firestore (USERS, CATALOG, REFERENCE_DATA).
  - Carga de los 9 pasos (seed) + pantalla de catálogo (RF-05/06) con mejor marca.
  - Ficha de paso + reproducción del video ideal en bucle (RF-07).
  - Cache offline del catálogo.

FASE 3 — Módulo de Pose
  - Platform channel MediaPipe (Android primero), interfaz PoseLandmarker.
  - Preview de cámara frontal en modo espejo (RF-09) con overlay de skeleton.
  - Validación de confianza/encuadre (RNF-05) + alerta "Cuerpo no detectado".

FASE 4 — Motor de evaluación
  - Portar FeatureExtractor + DTWComparator a Dart (sección 5).
  - Tests de regresión contra el prototipo Kotlin.

FASE 5 — Flujo de evaluación end-to-end
  - Pantalla evaluación: countdown 3 s (RF-08), grabación sincronizada (RN-07),
    extracción en vivo de landmarks, comparación con referencia.
  - Modal de resultados (RF-10): ritmo/alineación/total + feedback cualitativo.
  - Controles Salir / Siguiente paso (RF-11).
  - Guardado de intento local + actualización de mejor marca (RN-04).

FASE 6 — Perfil y progreso
  - Pantalla de perfil + editar perfil (RF-02), foto, progreso (RF-03/04).
  - Clasificación "Aprendido" / "En Práctica" (RN-02/03, umbral configurable).

FASE 7 — Offline-first y sincronización
  - Cola de intentos pendientes + motor de sync bidireccional (doc 5.3.3.2).
  - Resolución de conflictos last-write-wins; bitácora de sync reanudable.
  - (Opcional) Cloud Functions para métricas globales y validaciones servidor.

FASE 8 — Pulido
  - OAuth Google/Facebook, configuración, accesibilidad, manejo de errores,
    pruebas en 3 perfiles de hardware (gama alta/media/baja), latencia/FPS.
